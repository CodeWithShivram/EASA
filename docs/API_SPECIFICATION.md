# EASA — API Specification

> **Status:** health, document (Phase 2) search (Phase 3: semantic, keyword, hybrid), grounded answer and conversation (Phase 4), and tool and agent (Phase 5) endpoints are implemented. Other endpoint groups are planned and have **no contract yet**.
> Checked against the P2-M2 changes on 2026-11-14. The machine-readable schema is served at `/openapi.json` outside production.

Related: [LLD](LLD.md) · [Security](SECURITY.md) · [Architecture decisions](ARCHITECTURE_DECISIONS.md)

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1` (versioned in the path) |
| Format | JSON (`application/json`) for API responses |
| Correlation ID | Every HTTP response has `X-Correlation-ID`: 32 lowercase hex characters, generated by the server. A client-supplied `X-Correlation-ID` is ignored. The header is exposed to browsers through CORS |
| Errors | Standard error envelope (section 2), except where noted |
| Contracts | Explicit Pydantic request/response models; database models are never exposed directly |
| Authentication | None implemented yet (Phase 6). Document endpoints act as a development-only identity from server configuration ([ADR-014](ARCHITECTURE_DECISIONS.md#adr-014)) and are not mounted when `EASA_ENVIRONMENT=production` |
| Request size | Bodies larger than `EASA_MAX_UPLOAD_BYTES` + 64 KiB are rejected with `413 request_too_large`, whether declared in `Content-Length` or counted while streaming |
| CORS | Origins from `EASA_CORS_ALLOWED_ORIGINS` (default `http://localhost:3000`); methods `GET` only (browser uploads are not enabled until the frontend needs them); allowed request headers are the CORS-safelisted set (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`); credentials not allowed |
| Docs | `/docs` (Swagger UI) and `/openapi.json` are available when `EASA_ENVIRONMENT` is not `production` |

## 2. Error envelope

```json
{
  "error": {
    "code": "not_found",
    "message": "Not Found",
    "correlation_id": "46c7248531714c11804f9b4ceaff37f2"
  }
}
```

| Field | Type | Notes |
|---|---|---|
| `error.code` | string | Stable, machine-readable code |
| `error.message` | string | Safe for display; never contains stack traces or internal details |
| `error.correlation_id` | string or null | Same value as the `X-Correlation-ID` header |
| `error.details` | array, optional | Present only for validation errors: `[{ "location": [..], "message": "..", "type": ".." }]`. Submitted values are never echoed |

| Status | `code` | When |
|---|---|---|
| 400 | `invalid_content_length` | `Content-Length` header is not a non-negative integer |
| 404 | `not_found` | Unknown path |
| 405 | `method_not_allowed` | Wrong method on a known path; `Allow` header included |
| 413 | `request_too_large` | Request body over the limit (see Conventions) |
| 422 | `validation_error` | Invalid path, query or body parameters (e.g. malformed document ID, `limit` out of range, missing `file` field) |
| various | document-specific codes | See section 3.4 |
| 500 | `internal_error` | Unexpected server error; message `An unexpected error occurred.` |
| other 4xx/5xx from the framework | HTTP reason phrase in snake case | e.g. `service_unavailable` |

**Exceptions to the envelope**

- `GET /api/v1/health/ready` returns its own body with status 503 when not ready (section 3.2).
- A CORS preflight (`OPTIONS`) from an origin that is not allowed is answered by the CORS middleware with `400` and a plain-text body (`Disallowed CORS origin`). It still carries `X-Correlation-ID`.

## 3. Implemented endpoints

### 3.1 `GET /api/v1/health` — liveness

| Item | Specification |
|---|---|
| Purpose | Reports that the process is serving requests. Never touches the database or other dependencies, so it stays `200` even when the database is down |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body. Unknown query parameters are ignored |
| Response `200` | `{"status": "ok"}` — `status` is always the literal `"ok"` |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. One `request completed` JSON log line with the correlation ID, method, path, status and duration |

### 3.2 `GET /api/v1/health/ready` — readiness

| Item | Specification |
|---|---|
| Purpose | Reports whether required dependencies are usable: the database (`SELECT 1`), the configured embedding model (its pinned files are present; the model is not loaded) and, when answer generation is configured, the chat model (llama.cpp: `GET /health` is `200`, so the model has loaded, and `GET /v1/models` lists the configured name; Ollama: `GET /api/tags` lists it; each call has a 2-second timeout) |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body |
| Response `200` | `{"status": "ready", "checks": {"database": "ok", "embeddings": "ok", "model": "disabled"}}` |
| Response `503` | Any check `unavailable`, e.g. `{"status": "not_ready", "checks": {"database": "ok", "embeddings": "unavailable", "model": "disabled"}}` — a valid readiness answer, not an error envelope. `model: "disabled"` never causes `503` |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. The request log line as above; when the database check fails, a `database ping failed` warning with only the error type (no driver message or connection details); when the model check fails, a `model availability check failed` warning with only the error type |

Response schema:

| Field | Type | Values |
|---|---|---|
| `status` | string | `ready`, `not_ready` |
| `checks.database` | string | `ok`, `unavailable` |
| `checks.embeddings` | string | `ok`, `unavailable` (always `ok` for the `hashing` test provider) |
| `checks.model` | string | `ok`, `unavailable`, `disabled` (no chat model configured, `EASA_MODEL_PROVIDER=none`, the default) |

The web client accepts `503` as a valid result for this endpoint and validates both shapes with Zod; it displays the database check and ignores `checks.embeddings` and `checks.model` (unknown keys are stripped).

### 3.4 Documents (Phase 2, development only)

Common to all three endpoints:

| Item | Specification |
|---|---|
| Authentication | None yet. The server acts as the configured development identity (`EASA_DEV_TENANT_ID`, `EASA_DEV_USER_ID`); nothing in the request can change it |
| Authorization | Tenant isolation: only documents of the identity's tenant are visible. A document of another tenant answers exactly like a missing one (`404 document_not_found`) |
| Availability | Not mounted when `EASA_ENVIRONMENT=production` (all paths return `404 not_found`) |
| Audit | No audit records yet (Phase 5/6). Each request produces the standard `request completed` log line with its correlation ID |

Document object (`DocumentResponse`):

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | |
| `filename` | string | Sanitized display name (section 3.4.1 rules); never a storage path |
| `media_type` | string | `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document` or `text/plain`, decided by the server from the extension **and** content (the client's declared type is ignored) |
| `size_bytes` | integer | |
| `sha256` | string | Hex digest of the content |
| `status` | string | `uploaded`, `processing`, `processed`, `failed`. A new upload is processed within the request, so the response normally shows `processed` or `failed` (section 3.4.4) |
| `error_code` | string or null | Set when `status` is `failed` |
| `page_count` | integer or null | Number of PDF pages after successful processing; `null` for DOCX and TXT (no pages) and for failed documents |
| `chunking_config` | object or null | Chunking settings used for the stored chunks, e.g. `{"strategy": "structured", "max_chars": 1200, "overlap_chars": 150}`; `null` when the document has no chunks (failed) |
| `created_at`, `updated_at` | string | ISO 8601 UTC, e.g. `2026-11-14T09:58:28.943659Z` |

Tenant and owner IDs are not returned.

#### 3.4.1 `POST /api/v1/documents` — upload

| Item | Specification |
|---|---|
| Purpose | Store a PDF, DOCX or TXT file for the current tenant |
| Request | `multipart/form-data` with one file field named `file` |
| Response `201` | Document object; `Location: /api/v1/documents/{id}` |
| Response `200` | Same content was already uploaded in this tenant: the **existing** document is returned unchanged (idempotent; the new filename is ignored) |
| Validation | 1. Filename: last path component only (both `/` and `\`), Unicode NFC, whitespace (including tabs, newlines, NEL) → spaces, C0/C1 control characters, zero-width characters, Unicode bidirectional controls and `< > : " / \ \| ? *` removed, trailing dots and spaces removed; must not be empty or start with a dot; truncated to 255 characters keeping the extension. 2. Extension allowlist: `.pdf`, `.docx`, `.txt` (case-insensitive). 3. Size: 1 byte to `EASA_MAX_UPLOAD_BYTES` (default 10 MiB). 4. Content must match the extension: PDF starts with `%PDF-`; DOCX is a readable zip with `[Content_Types].xml` and `word/document.xml`, at most 1000 entries, 100 MiB total uncompressed, compression ratio ≤ 200 per entry, no encrypted entries, no VBA macro part; TXT is valid UTF-8 (BOM allowed), contains no NUL bytes and is not a PDF or zip |

Upload error codes (all use the error envelope):

| Status | `code` | Meaning |
|---|---|---|
| 400 | `invalid_filename` | Missing, empty or dot-prefixed name |
| 413 | `file_too_large` | File over `EASA_MAX_UPLOAD_BYTES` |
| 413 | `request_too_large` | Whole request body over the limit |
| 415 | `unsupported_file_type` | Extension not allowed |
| 415 | `file_content_mismatch` | Content does not match the extension |
| 422 | `empty_file` | Zero bytes |
| 422 | `invalid_text_encoding` | TXT is not UTF-8 |
| 422 | `corrupt_file` | DOCX zip cannot be read |
| 422 | `encrypted_file` | DOCX contains encrypted entries |
| 422 | `archive_limits_exceeded` | DOCX exceeds entry, size or compression-ratio limits (zip-bomb protection) |
| 422 | `macros_not_allowed` | DOCX contains a VBA macro part (`vbaProject.bin`) |
| 422 | `validation_error` | No `file` field |

Encrypted PDFs are detected during processing, because that requires parsing the PDF: the upload succeeds (`201`) and the document is stored as `failed` with `encrypted_file` (section 3.4.4).

#### 3.4.2 `GET /api/v1/documents` — list

| Item | Specification |
|---|---|
| Purpose | List the current tenant's documents, newest first |
| Query | `limit` integer 1–200 (default 50); `offset` integer ≥ 0 (default 0) |
| Response `200` | `{"items": [Document, ...], "limit": n, "offset": n}` |
| Errors | `422 validation_error` for out-of-range `limit`/`offset` |

#### 3.4.3 `GET /api/v1/documents/{document_id}` — get

| Item | Specification |
|---|---|
| Purpose | Return one of the current tenant's documents |
| Path | `document_id`: UUID |
| Response `200` | Document object |
| Errors | `404 document_not_found` (missing or another tenant's); `422 validation_error` for a malformed UUID |

#### 3.4.4 Processing outcome

A newly created document is processed (text extraction, normalization and chunking) before the upload response is sent. Processing problems do **not** fail the HTTP request: the upload returns `201` and the document records the outcome. An identical re-upload returns the existing document without reprocessing it.

| Final `status` | `error_code` | Meaning |
|---|---|---|
| `processed` | `null` | Text extracted |
| `failed` | `encrypted_file` | Password-protected PDF (all encrypted PDFs are rejected) |
| `failed` | `corrupt_file` | The PDF or DOCX cannot be parsed |
| `failed` | `too_many_pages` | PDF has more than `EASA_MAX_PDF_PAGES` pages (default 500) |
| `failed` | `resource_limit_exceeded` | A PDF exceeds a parsing limit: a stream inflating beyond 20 MB, more than 50 MB decoded in total, or more than 30 seconds of parsing |
| `failed` | `text_too_large` | More than 5,000,000 characters of normalized text |
| `failed` | `document_too_complex` | More than 50,000 text blocks or more than 20,000 chunks |
| `failed` | `no_extractable_text` | No text found, e.g. a scanned PDF without a text layer (OCR is not supported) or a whitespace-only TXT |
| `failed` | `processing_error` | Unexpected parser failure; details are logged server-side only |

`processing` is normally visible only while a request is in progress. If processing was interrupted (for example the server process died), the document stays `processing`; an identical re-upload more than 10 minutes later reprocesses it and returns the result with `200`.

#### 3.4.5 `GET /api/v1/documents/{document_id}/chunks` — chunks

| Item | Specification |
|---|---|
| Purpose | Return a document's chunks in order, with their location metadata |
| Authentication / authorization | As for all document endpoints: development identity, tenant isolation |
| Path | `document_id`: UUID |
| Query | `limit` integer 1–500 (default 100); `offset` integer ≥ 0 (default 0) |
| Response `200` | `{"document_id": UUID, "items": [Chunk, ...], "total": n, "limit": n, "offset": n}`; `items` is empty for documents that failed processing |
| Errors | `404 document_not_found` (missing or another tenant's); `422 validation_error` for a malformed UUID or out-of-range `limit`/`offset` |
| Audit | No audit record yet; standard request log line |

Chunk object:

| Field | Type | Notes |
|---|---|---|
| `chunk_index` | integer | 0-based, consecutive per document |
| `text` | string | Normalized chunk text |
| `page_number` | integer or null | 1-based PDF page where the chunk starts; `null` for DOCX and TXT |
| `section` | string or null | Nearest preceding heading (DOCX); `null` when unknown |
| `char_start`, `char_end` | integer | Offsets into the document's canonical normalized text (blocks joined by a blank line); `char_end - char_start` equals the text length |

Chunk text is document content: it is returned only to the owning tenant and is never written to logs.

### 3.5 `POST /api/v1/search` — semantic, keyword and hybrid search (Phase 3, development only)

| Item | Specification |
|---|---|
| Purpose | Find the chunks of the current tenant's documents that best match a query, with citations. Modes: `semantic` (embedding similarity), `keyword` (BM25 full-text search) or `hybrid` (both, fused) |
| Authentication / authorization | As for document endpoints: development identity; only the identity's tenant is searched. The tenant, "processed documents only" and embedding-model filters are applied in the database query **before** any scoring, so other tenants' content is never scored or returned |
| Availability | Not mounted when `EASA_ENVIRONMENT=production` |
| Request | JSON `{"query": string, "top_k": integer, "mode": string}`. `query`: 1–1,000 characters; `top_k`: 1–50, default 5; `mode`: `hybrid` (default since P4-M2; `semantic` before), `semantic` or `keyword`. Unknown fields are rejected |
| Validation | The query is normalized like chunk text (Unicode NFC, invisible characters removed, whitespace collapsed); a query that is empty after normalization is rejected. For keyword search, the query is reduced to at most 32 distinct word tokens, each quoted and joined with `OR`, so full-text query syntax (operators, column filters, quotes) cannot be injected; a query with no word characters returns no keyword results |
| Response `200` | `{"mode": string, "model_id": string or null, "results": [{"score": number, "text": string, "citation": Citation}, ...]}`, ordered by score (highest first); ties are broken by chunk ID. `model_id` is `null` in `keyword` mode. `results` may be empty |
| Errors | `422 validation_error` (missing or out-of-range fields, unknown fields or modes); `422 empty_query`; `503 embeddings_unavailable` (`semantic` and `hybrid` only; `keyword` works without the model); `503 keyword_search_unavailable` (the keyword implementation does not match the database; not expected in normal operation, since the implementation is chosen from the database) |
| Audit | No audit record yet. One `search completed` log line with mode, model ID, `top_k`, result count and duration; **the query text is never logged** |

Citation object:

| Field | Type | Notes |
|---|---|---|
| `document_id` | UUID | |
| `filename` | string | Sanitized display name |
| `page_number` | integer or null | PDF page; `null` for DOCX and TXT |
| `section` | string or null | Nearest heading (DOCX) |
| `chunk_index` | integer | |
| `char_start`, `char_end` | integer | Offsets into the document's canonical normalized text |

Score meaning depends on the mode, and scores are never comparable across modes:

| Mode | `score` |
|---|---|
| `semantic` | Cosine similarity between query and chunk embeddings (−1 to 1; vectors are L2-normalized), computed by NumPy on SQLite or by pgvector on PostgreSQL (equal up to float rounding). Comparable only within one `model_id`. With the `hashing` test provider it reflects word overlap, not meaning |
| `keyword` | Database-specific relevance, higher is better. SQLite: negated FTS5 BM25 rank (unbounded). PostgreSQL: `ts_rank_cd` (0 or more). Both stem English words: "leave" matches "leaves" |
| `hybrid` | Reciprocal Rank Fusion: the sum of `1 / (60 + rank)` over the semantic and keyword rankings (each taking the top `max(4 × top_k, 20)` candidates); at most 2/61 ≈ 0.0328 |

None of these are probabilities.

### 3.6 `POST /api/v1/answers` — grounded answers (Phase 4, development only)

| Item | Specification |
|---|---|
| Purpose | Answer a question using only the current tenant's documents, with cited sources, or say that the evidence is insufficient |
| Authentication | None yet; uses the development-only identity (ADR-014). Not mounted in production |
| Authorization | Evidence comes only from the identity's tenant and from processed documents (the same filters as section 3.5) |
| Request | JSON `{"question": string, "top_k": integer}`. `question`: 1–1,000 characters; `top_k`: chunks retrieved as evidence, 1–10, default 3 (5 before ADR-027). Unknown fields are rejected |
| Processing | Hybrid search (top `top_k`) → numbered sources `[S1]`…`[Sn]` within a 6,000-character budget → the configured chat model, instructed to use only the sources, cite them and reply `INSUFFICIENT_EVIDENCE` otherwise → reply checks (marker or a refusal phrased in words, citations) |
| Response `200` | `{"status": "answered" or "insufficient_evidence", "answer": string or null, "reason": string or null, "sources": [{"label": string, "text": string, "citation": Citation}, ...], "retrieved": integer, "model_id": string or null}` |
| Errors | `422 validation_error` (missing or out-of-range fields, unknown fields); `422 empty_query`; `503 answers_unavailable` (no chat model configured, `EASA_MODEL_PROVIDER=none`); `503 model_unavailable` (model server unreachable or model not installed); `502 model_error` (the model timed out, failed or replied malformed); `503 embeddings_unavailable` (hybrid retrieval needs the embedding model) |
| Audit | No audit record yet. One `answer completed` log line with status, reason, retrieved and cited counts, model ID, token counts and duration; **the question and the answer are never logged** |

Response fields:

| Field | Meaning |
|---|---|
| `status` | `answered`, or `insufficient_evidence` when the documents do not support an answer |
| `answer` | The model's answer with `[S#]` citation markers; `null` unless `answered`. Markers for sources that were not provided are removed |
| `reason` | `null` when answered; otherwise `no_results` (nothing retrieved; the model is not called), `model_declined` (the model replied `INSUFFICIENT_EVIDENCE`, nothing, or said in words that the sources do not provide the information) or `no_valid_citations` (the reply cited no provided source, so it is withheld) |
| `sources` | Only the sources the answer cites, in order of first citation. `text` is exactly what the model saw (a source cut to fit the budget ends with ` ...`); `citation` as in section 3.5 |
| `retrieved` | Chunks retrieved before the model was asked |
| `model_id` | The chat model that replied, e.g. `ollama:<model>` or `fake-chat-v1`; `null` when the model was not called |

`insufficient_evidence` is a successful response, not an error. Answers are generated text: they can still be wrong even when cited, and the citations are the way to check them.

### 3.7 Conversations (Phase 4, development only)

Multi-turn grounded answering. A conversation belongs to the current user in the current tenant (development identity, ADR-014); any other user's or tenant's conversation returns the same `404 conversation_not_found` as a missing one. Not mounted in production.

| Endpoint | Request | Response |
|---|---|---|
| `POST /api/v1/conversations` | No body | `201` `{"id", "created_at", "updated_at", "messages": 0}` |
| `GET /api/v1/conversations?limit=20` | `limit` 1–100 | `200` `{"items": [{"id", "created_at", "updated_at", "messages"}, ...]}`, own conversations only, most recently updated first |
| `GET /api/v1/conversations/{id}` | | `200` `{"id", "created_at", "updated_at", "messages": [Message, ...]}` in order; `404` |
| `POST /api/v1/conversations/{id}/messages` | `{"question": string, "top_k": integer}` as in section 3.6 (unknown fields rejected) | `200` `{"conversation_id", "turn", "answer": AnswerResponse}` where `answer` has exactly the shape of section 3.6 (including source text) |
| `DELETE /api/v1/conversations/{id}` | | `204`; the conversation and its messages are deleted permanently; `404` |

`Message`: `{"id", "position", "role": "user" or "assistant", "content": string or null, "status", "reason", "sources": [{"label", "citation": Citation}], "model_id", "created_at"}`. Stored sources contain citation metadata only, **not** the chunk text; `status`, `reason`, `sources` and `model_id` are set on assistant messages.

Follow-ups: retrieval searches the previous question plus the new one (within the 1,000-character search limit); the prompt includes the last 2 turns (at most 1,500 characters, old citation markers removed) in a `<history>` element that the model is told is context, not evidence. Citations are checked against the current sources only.

Errors for asking: those of section 3.6, plus `404 conversation_not_found`, `409 conversation_full` (50 questions per conversation) and `409 conversation_busy` (another request added a turn at the same time; ask again). A question and its reply are stored only when the answer pipeline succeeds; on any error nothing is stored. `422 validation_error` for malformed IDs, bodies or limits.

Audit: no audit record yet. Log lines `conversation created`, `conversation turn stored` (conversation ID, turn number, history turns used, status) and `conversation deleted`; **questions and answers are never logged**.
### 3.8 Tools (Phase 5, development only)

Direct access to the allowlisted tools through the same executor the agent will use, for development and testing. Uses the development identity and its configured permissions (`EASA_DEV_PERMISSIONS`). Not mounted in production.

| Endpoint | Request | Response |
|---|---|---|
| `GET /api/v1/tools` | | `200` `{"items": [{"name", "description", "consequential", "input_schema"}, ...]}`: only tools the identity may use |
| `POST /api/v1/tools/{name}/invoke` | `{"arguments": {...}}` (unknown top-level fields rejected; `name` at most 64 characters) | `200` `{"tool", "outcome", "output", "arguments", "detail", "message"}` |

Tool outcomes are reported in the body with status `200`; only a malformed request is an error (`422 validation_error`). `outcome` is one of `succeeded` (with `output`), `confirmation_required` (consequential tools; nothing ran; `arguments` shows what would run; confirming arrives with the agent in P5-M3), `denied` (`detail` = missing permission), `unknown_tool`, `invalid_arguments` (`detail` `schema` or `arguments_too_large`), `failed` (`detail` = error code such as `ticket_not_found`, or an error type) or `timeout`. `message` is always safe to display.

| Tool | Permission | Input | Output |
|---|---|---|---|
| `search_knowledge_base` | `knowledge:search` | `{"query": string 1–1,000}` | `{"results": [{"filename", "page_number", "section", "text"}]}` (top 3 hybrid hits of the tenant, text at most 600 characters) |
| `get_ticket` | `tickets:read` | `{"number": integer ≥ 1}` | `{"number", "title", "description", "status", "priority", "created_at", "updated_at"}`; own tickets only, otherwise `failed` / `ticket_not_found` |
| `get_ticket_status` | `tickets:read` | `{"number": integer ≥ 1}` | `{"number", "status", "updated_at"}` |
| `create_draft_ticket` (consequential) | `tickets:create` | `{"title": 5–200, "description": 10–2,000, "priority": "low"/"normal"/"high" (default normal)}` | `{"number", "status": "draft", "title"}` |

Audit: every invocation writes one `audit_logs` record (section 1.2b of DATABASE_DESIGN) and one `tool call finished` log line with metadata only; arguments and outputs are never logged.

### 3.9 Agent (Phase 5, development only)

The agent handles a request by proposing steps that the server checks and runs. Uses the development identity and its permissions; needs a configured chat model. Not mounted in production.

| Endpoint | Request | Response |
|---|---|---|
| `POST /api/v1/agent` | `{"message": string 1–1,000}` (unknown fields rejected) | `200` `{"status", "answer", "reason", "steps": [{"tool", "outcome", "detail"}], "pending_action": PendingAction or null, "model_id"}` |
| `GET /api/v1/agent/actions/{id}` | | `200` PendingAction; `404 action_not_found` |
| `POST /api/v1/agent/actions/{id}/confirm` | | `200` `{"action": PendingAction, "result": ToolResult}` (ToolResult as in section 3.8); `404`; `409 action_expired` or `409 action_not_pending` |
| `POST /api/v1/agent/actions/{id}/cancel` | | `200` PendingAction; `404`; `409` as above |

`status`: `answered`, `confirmation_required` (a consequential tool was proposed; nothing ran; see `pending_action`; `answer` is a server-written prompt stating exactly what would run) or `failed` (`reason` `invalid_model_output`, or `too_many_pending_actions` when the user already has 20 open actions). An `answered` result has `reason` `unsupported_claim` when the model's answer reported a change that no tool result showed; `answer` is then "I can't do that, and nothing has been changed." (ADR-030). In a proposal, the draft ticket's `priority` is kept only when the user's message states it; otherwise it is `normal`. `steps` lists every tool call the model proposed with its executor outcome (section 3.8) or `repeated` (an identical call that was not run again). PendingAction: `{"id", "tool", "arguments", "status": "pending"/"confirmed"/"failed"/"cancelled", "result", "created_at", "expires_at", "decided_at"}`.

Behaviour: each model reply is constrained to a JSON schema offering only the tools the caller may use plus a final answer; at most 3 tool calls, then only a final answer; tool results return to the model in escaped `<tool_result>` elements as data. Confirming runs the tool once, with the permission checked again at that moment; an action expires 10 minutes after it was proposed. The final answer is generated text and is not citation-checked.

Errors: `422 validation_error` / `invalid_message`; `503 agent_unavailable` (no model configured) or `model_unavailable`; `502 model_error`. Audit: every tool call is an `audit_logs` record (section 3.8); one `agent run finished` log line with status and step outcomes; messages and answers are never logged.

## 4. Headers

| Header | Direction | Notes |
|---|---|---|
| `X-Correlation-ID` | response | Always present on HTTP responses; include it when reporting a problem |
| `Access-Control-Allow-Origin` | response | Only for allowed origins |
| `Access-Control-Expose-Headers` | response | Includes `X-Correlation-ID` |
| `Allow` | response | On `405` |
| `Accept: application/json` | request | Sent by the web client |

## 6. Known gaps

- No authentication or rate limiting yet. Document endpoints use a development-only identity and are disabled in production.
- Uploads are only accepted from non-browser clients for now (CORS allows `GET` only).
- Health endpoints are public. They expose only coarse status.
- Only `GET` is allowed by CORS; this will widen as endpoints are added.
