# EASA — API Specification

> **Status:** health endpoints and the first document endpoints (upload, list, get; Phase 2, P2-M2) are implemented. Other endpoint groups are planned and have **no contract yet**.
> Checked against the P2-M2 changes on 2026-11-14. The machine-readable schema is served at `/openapi.json` outside production.

Related: [LLD](LLD.md) · [Security](SECURITY.md) · [Architecture decisions](ARCHITECTURE_DECISIONS.md)

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1` (versioned in the path) |
| Format | JSON (`application/json`) for API responses |
| Correlation ID | Every HTTP response has `X-Correlation-ID`: 32 lowercase hex characters, generated by the server. A client-supplied `X-Correlation-ID` is ignored. The header is exposed to browsers through CORS |
| Errors | Standard error envelope (section 2), except where noted |
| Contracts | Explicit Pydantic request/response models; database models are never exposed directly |
| Authentication | None implemented yet (Phase 6). Document endpoints act as a development-only identity from server configuration ([ADR-014](ARCHITECTURE_DECISIONS.md#adr-014)) and are not mounted when `EASA_ENVIRONMENT=production` |
| Request size | Bodies larger than `EASA_MAX_UPLOAD_BYTES` + 64 KiB are rejected with `413 request_too_large`, whether declared in `Content-Length` or counted while streaming |
| CORS | Origins from `EASA_CORS_ALLOWED_ORIGINS` (default `http://localhost:3000`); methods `GET` only (browser uploads are not enabled until the frontend needs them); allowed request headers are the CORS-safelisted set (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`); credentials not allowed |
| Docs | `/docs` (Swagger UI) and `/openapi.json` are available when `EASA_ENVIRONMENT` is not `production` |

## 2. Error envelope

```json
{
  "error": {
    "code": "not_found",
    "message": "Not Found",
    "correlation_id": "46c7248531714c11804f9b4ceaff37f2"
  }
}
```

| Field | Type | Notes |
|---|---|---|
| `error.code` | string | Stable, machine-readable code |
| `error.message` | string | Safe for display; never contains stack traces or internal details |
| `error.correlation_id` | string or null | Same value as the `X-Correlation-ID` header |
| `error.details` | array, optional | Present only for validation errors: `[{ "location": [..], "message": "..", "type": ".." }]`. Submitted values are never echoed |

| Status | `code` | When |
|---|---|---|
| 400 | `invalid_content_length` | `Content-Length` header is not a non-negative integer |
| 404 | `not_found` | Unknown path |
| 405 | `method_not_allowed` | Wrong method on a known path; `Allow` header included |
| 413 | `request_too_large` | Request body over the limit (see Conventions) |
| 422 | `validation_error` | Invalid path, query or body parameters (e.g. malformed document ID, `limit` out of range, missing `file` field) |
| various | document-specific codes | See section 3.4 |
| 500 | `internal_error` | Unexpected server error; message `An unexpected error occurred.` |
| other 4xx/5xx from the framework | HTTP reason phrase in snake case | e.g. `service_unavailable` |

**Exceptions to the envelope**

- `GET /api/v1/health/ready` returns its own body with status 503 when not ready (section 3.2).
- A CORS preflight (`OPTIONS`) from an origin that is not allowed is answered by the CORS middleware with `400` and a plain-text body (`Disallowed CORS origin`). It still carries `X-Correlation-ID`.

## 3. Implemented endpoints

### 3.1 `GET /api/v1/health` — liveness

| Item | Specification |
|---|---|
| Purpose | Reports that the process is serving requests. Never touches the database or other dependencies, so it stays `200` even when the database is down |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body. Unknown query parameters are ignored |
| Response `200` | `{"status": "ok"}` — `status` is always the literal `"ok"` |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. One `request completed` JSON log line with the correlation ID, method, path, status and duration |

### 3.2 `GET /api/v1/health/ready` — readiness

| Item | Specification |
|---|---|
| Purpose | Reports whether required dependencies are usable. Currently checks the database with `SELECT 1` |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body |
| Response `200` | `{"status": "ready", "checks": {"database": "ok"}}` |
| Response `503` | `{"status": "not_ready", "checks": {"database": "unavailable"}}` — a valid readiness answer, not an error envelope |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. The request log line as above; when the database check fails, a `database ping failed` warning with only the error type (no driver message or connection details) |

Response schema:

| Field | Type | Values |
|---|---|---|
| `status` | string | `ready`, `not_ready` |
| `checks.database` | string | `ok`, `unavailable` |

The web client accepts `503` as a valid result for this endpoint and validates both shapes with Zod.

### 3.3 Framework endpoints (non-production only)

| Path | Purpose |
|---|---|
| `GET /docs` | Swagger UI |
| `GET /openapi.json` | OpenAPI schema |

Both return `404` when `EASA_ENVIRONMENT=production`. ReDoc is disabled.

### 3.4 Documents (Phase 2, development only)

Common to all three endpoints:

| Item | Specification |
|---|---|
| Authentication | None yet. The server acts as the configured development identity (`EASA_DEV_TENANT_ID`, `EASA_DEV_USER_ID`); nothing in the request can change it |
| Authorization | Tenant isolation: only documents of the identity's tenant are visible. A document of another tenant answers exactly like a missing one (`404 document_not_found`) |
| Availability | Not mounted when `EASA_ENVIRONMENT=production` (all paths return `404 not_found`) |
| Audit | No audit records yet (Phase 5/6). Each request produces the standard `request completed` log line with its correlation ID |

Document object (`DocumentResponse`):

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | |
| `filename` | string | Sanitized display name (section 3.4.1 rules); never a storage path |
| `media_type` | string | `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document` or `text/plain`, decided by the server from the extension **and** content (the client's declared type is ignored) |
| `size_bytes` | integer | |
| `sha256` | string | Hex digest of the content |
| `status` | string | `uploaded`, `processing`, `processed`, `failed`. A new upload is processed within the request, so the response normally shows `processed` or `failed` (section 3.4.4) |
| `error_code` | string or null | Set when `status` is `failed` |
| `page_count` | integer or null | Number of PDF pages after successful processing; `null` for DOCX and TXT (no pages) and for failed documents |
| `chunking_config` | object or null | Chunking settings used for the stored chunks, e.g. `{"strategy": "structured", "max_chars": 1200, "overlap_chars": 150}`; `null` when the document has no chunks (failed) |
| `created_at`, `updated_at` | string | ISO 8601 UTC, e.g. `2026-11-14T09:58:28.943659Z` |

Tenant and owner IDs are not returned.

#### 3.4.1 `POST /api/v1/documents` — upload

| Item | Specification |
|---|---|
| Purpose | Store a PDF, DOCX or TXT file for the current tenant |
| Request | `multipart/form-data` with one file field named `file` |
| Response `201` | Document object; `Location: /api/v1/documents/{id}` |
| Response `200` | Same content was already uploaded in this tenant: the **existing** document is returned unchanged (idempotent; the new filename is ignored) |
| Validation | 1. Filename: last path component only (both `/` and `\`), Unicode NFC, whitespace (including tabs, newlines, NEL) → spaces, C0/C1 control characters, zero-width characters, Unicode bidirectional controls and `< > : " / \ \| ? *` removed, trailing dots and spaces removed; must not be empty or start with a dot; truncated to 255 characters keeping the extension. 2. Extension allowlist: `.pdf`, `.docx`, `.txt` (case-insensitive). 3. Size: 1 byte to `EASA_MAX_UPLOAD_BYTES` (default 10 MiB). 4. Content must match the extension: PDF starts with `%PDF-`; DOCX is a readable zip with `[Content_Types].xml` and `word/document.xml`, at most 1000 entries, 100 MiB total uncompressed, compression ratio ≤ 200 per entry, no encrypted entries, no VBA macro part; TXT is valid UTF-8 (BOM allowed), contains no NUL bytes and is not a PDF or zip |

Upload error codes (all use the error envelope):

| Status | `code` | Meaning |
|---|---|---|
| 400 | `invalid_filename` | Missing, empty or dot-prefixed name |
| 413 | `file_too_large` | File over `EASA_MAX_UPLOAD_BYTES` |
| 413 | `request_too_large` | Whole request body over the limit |
| 415 | `unsupported_file_type` | Extension not allowed |
| 415 | `file_content_mismatch` | Content does not match the extension |
| 422 | `empty_file` | Zero bytes |
| 422 | `invalid_text_encoding` | TXT is not UTF-8 |
| 422 | `corrupt_file` | DOCX zip cannot be read |
| 422 | `encrypted_file` | DOCX contains encrypted entries |
| 422 | `archive_limits_exceeded` | DOCX exceeds entry, size or compression-ratio limits (zip-bomb protection) |
| 422 | `macros_not_allowed` | DOCX contains a VBA macro part (`vbaProject.bin`) |
| 422 | `validation_error` | No `file` field |

Encrypted PDFs are detected during processing, because that requires parsing the PDF: the upload succeeds (`201`) and the document is stored as `failed` with `encrypted_file` (section 3.4.4).

#### 3.4.2 `GET /api/v1/documents` — list

| Item | Specification |
|---|---|
| Purpose | List the current tenant's documents, newest first |
| Query | `limit` integer 1–200 (default 50); `offset` integer ≥ 0 (default 0) |
| Response `200` | `{"items": [Document, ...], "limit": n, "offset": n}` |
| Errors | `422 validation_error` for out-of-range `limit`/`offset` |

#### 3.4.3 `GET /api/v1/documents/{document_id}` — get

| Item | Specification |
|---|---|
| Purpose | Return one of the current tenant's documents |
| Path | `document_id`: UUID |
| Response `200` | Document object |
| Errors | `404 document_not_found` (missing or another tenant's); `422 validation_error` for a malformed UUID |

#### 3.4.4 Processing outcome

A newly created document is processed (text extraction, normalization and chunking) before the upload response is sent. Processing problems do **not** fail the HTTP request: the upload returns `201` and the document records the outcome. An identical re-upload returns the existing document without reprocessing it.

| Final `status` | `error_code` | Meaning |
|---|---|---|
| `processed` | `null` | Text extracted |
| `failed` | `encrypted_file` | Password-protected PDF (all encrypted PDFs are rejected) |
| `failed` | `corrupt_file` | The PDF or DOCX cannot be parsed |
| `failed` | `too_many_pages` | PDF has more than `EASA_MAX_PDF_PAGES` pages (default 500) |
| `failed` | `resource_limit_exceeded` | A PDF exceeds a parsing limit: a stream inflating beyond 20 MB, more than 50 MB decoded in total, or more than 30 seconds of parsing |
| `failed` | `text_too_large` | More than 5,000,000 characters of normalized text |
| `failed` | `document_too_complex` | More than 50,000 text blocks or more than 20,000 chunks |
| `failed` | `no_extractable_text` | No text found, e.g. a scanned PDF without a text layer (OCR is not supported) or a whitespace-only TXT |
| `failed` | `processing_error` | Unexpected parser failure; details are logged server-side only |

`processing` is normally visible only while a request is in progress. If processing was interrupted (for example the server process died), the document stays `processing`; an identical re-upload more than 10 minutes later reprocesses it and returns the result with `200`.

#### 3.4.5 `GET /api/v1/documents/{document_id}/chunks` — chunks

| Item | Specification |
|---|---|
| Purpose | Return a document's chunks in order, with their location metadata |
| Authentication / authorization | As for all document endpoints: development identity, tenant isolation |
| Path | `document_id`: UUID |
| Query | `limit` integer 1–500 (default 100); `offset` integer ≥ 0 (default 0) |
| Response `200` | `{"document_id": UUID, "items": [Chunk, ...], "total": n, "limit": n, "offset": n}`; `items` is empty for documents that failed processing |
| Errors | `404 document_not_found` (missing or another tenant's); `422 validation_error` for a malformed UUID or out-of-range `limit`/`offset` |
| Audit | No audit record yet; standard request log line |

Chunk object:

| Field | Type | Notes |
|---|---|---|
| `chunk_index` | integer | 0-based, consecutive per document |
| `text` | string | Normalized chunk text |
| `page_number` | integer or null | 1-based PDF page where the chunk starts; `null` for DOCX and TXT |
| `section` | string or null | Nearest preceding heading (DOCX); `null` when unknown |
| `char_start`, `char_end` | integer | Offsets into the document's canonical normalized text (blocks joined by a blank line); `char_end - char_start` equals the text length |

Chunk text is document content: it is returned only to the owning tenant and is never written to logs.

## 4. Headers

| Header | Direction | Notes |
|---|---|---|
| `X-Correlation-ID` | response | Always present on HTTP responses; include it when reporting a problem |
| `Access-Control-Allow-Origin` | response | Only for allowed origins |
| `Access-Control-Expose-Headers` | response | Includes `X-Correlation-ID` |
| `Allow` | response | On `405` |
| `Accept: application/json` | request | Sent by the web client |

## 6. Known gaps

- No authentication or rate limiting yet. Document endpoints use a development-only identity and are disabled in production.
- Uploads are only accepted from non-browser clients for now (CORS allows `GET` only).
- Health endpoints are public. They expose only coarse status.
- Only `GET` is allowed by CORS; this will widen as endpoints are added.
