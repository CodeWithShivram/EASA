# EASA — API Specification

> **Status:** two endpoints are implemented (liveness and readiness). Other endpoint groups are planned and have **no contract yet**.
> Checked against the M5 state (commit `3371ec3` plus M5 changes) on 2026-11-14. The machine-readable schema is served at `/openapi.json` outside production.

Related: [LLD](LLD.md) · [Security](SECURITY.md) · [Architecture decisions](ARCHITECTURE_DECISIONS.md)

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1` (versioned in the path) |
| Format | JSON (`application/json`) for API responses |
| Correlation ID | Every HTTP response has `X-Correlation-ID`: 32 lowercase hex characters, generated by the server. A client-supplied `X-Correlation-ID` is ignored. The header is exposed to browsers through CORS |
| Errors | Standard error envelope (section 2), except where noted |
| Contracts | Explicit Pydantic request/response models; database models are never exposed directly |
| Authentication | None implemented yet. Planned for Phase 6 |
| CORS | Origins from `EASA_CORS_ALLOWED_ORIGINS` (default `http://localhost:3000`); methods `GET`; allowed request headers are the CORS-safelisted set (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`); credentials not allowed |
| Docs | `/docs` (Swagger UI) and `/openapi.json` are available when `EASA_ENVIRONMENT` is not `production` |

## 2. Error envelope

```json
{
  "error": {
    "code": "not_found",
    "message": "Not Found",
    "correlation_id": "46c7248531714c11804f9b4ceaff37f2"
  }
}
```

| Field | Type | Notes |
|---|---|---|
| `error.code` | string | Stable, machine-readable code |
| `error.message` | string | Safe for display; never contains stack traces or internal details |
| `error.correlation_id` | string or null | Same value as the `X-Correlation-ID` header |
| `error.details` | array, optional | Present only for validation errors: `[{ "location": [..], "message": "..", "type": ".." }]`. Submitted values are never echoed |

| Status | `code` | When |
|---|---|---|
| 404 | `not_found` | Unknown path |
| 405 | `method_not_allowed` | Wrong method on a known path; `Allow` header included |
| 422 | `validation_error` | Invalid path, query or body parameters (no current endpoint accepts parameters, so this applies to future endpoints) |
| 500 | `internal_error` | Unexpected server error; message `An unexpected error occurred.` |
| other 4xx/5xx from the framework | HTTP reason phrase in snake case | e.g. `service_unavailable` |

**Exceptions to the envelope**

- `GET /api/v1/health/ready` returns its own body with status 503 when not ready (section 3.2).
- A CORS preflight (`OPTIONS`) from an origin that is not allowed is answered by the CORS middleware with `400` and a plain-text body (`Disallowed CORS origin`). It still carries `X-Correlation-ID`.

## 3. Implemented endpoints

### 3.1 `GET /api/v1/health` — liveness

| Item | Specification |
|---|---|
| Purpose | Reports that the process is serving requests. Never touches the database or other dependencies, so it stays `200` even when the database is down |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body. Unknown query parameters are ignored |
| Response `200` | `{"status": "ok"}` — `status` is always the literal `"ok"` |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. One `request completed` JSON log line with the correlation ID, method, path, status and duration |

### 3.2 `GET /api/v1/health/ready` — readiness

| Item | Specification |
|---|---|
| Purpose | Reports whether required dependencies are usable. Currently checks the database with `SELECT 1` |
| Authentication | None (public) |
| Authorization | None |
| Request | No parameters or body |
| Response `200` | `{"status": "ready", "checks": {"database": "ok"}}` |
| Response `503` | `{"status": "not_ready", "checks": {"database": "unavailable"}}` — a valid readiness answer, not an error envelope |
| Errors | `405` envelope for other methods; `500` envelope on unexpected failure |
| Validation | None (no input) |
| Audit | No audit record. The request log line as above; when the database check fails, a `database ping failed` warning with only the error type (no driver message or connection details) |

Response schema:

| Field | Type | Values |
|---|---|---|
| `status` | string | `ready`, `not_ready` |
| `checks.database` | string | `ok`, `unavailable` |

The web client accepts `503` as a valid result for this endpoint and validates both shapes with Zod.

### 3.3 Framework endpoints (non-production only)

| Path | Purpose |
|---|---|
| `GET /docs` | Swagger UI |
| `GET /openapi.json` | OpenAPI schema |

Both return `404` when `EASA_ENVIRONMENT=production`. ReDoc is disabled.

## 4. Headers

| Header | Direction | Notes |
|---|---|---|
| `X-Correlation-ID` | response | Always present on HTTP responses; include it when reporting a problem |
| `Access-Control-Allow-Origin` | response | Only for allowed origins |
| `Access-Control-Expose-Headers` | response | Includes `X-Correlation-ID` |
| `Allow` | response | On `405` |
| `Accept: application/json` | request | Sent by the web client |

| `/api/v1/auth` | Sign-in and identity | 6 |

Each will be documented here with purpose, authentication, authorization, request and response schemas, errors, validation rules and audit behaviour before or with its implementation. Protected endpoints will deny access by default and resolve identity from a verified authentication context.

## 6. Known gaps

- No authentication, rate limiting or request size limits yet.
- Health endpoints are public. They expose only coarse status.
- Only `GET` is allowed by CORS; this will widen as endpoints are added.
